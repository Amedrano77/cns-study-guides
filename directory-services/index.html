1. Active Directory Overview

1.1 What is Active Directory?

Active Directory Domain Services (AD DS) is Microsoft's directory service — a centralized database that stores information about users, computers, groups, printers, and other network resources. It provides authentication (who are you?) and authorization (what can you access?) for an entire organization from a single point of administration.

1.2 Key Benefits of AD DS

  • Centralized authentication: One username/password works on any domain-joined computer
  • Centralized policy: Group Policy pushes settings, software, and restrictions to all computers
  • Single Sign-On (SSO): Log in once, access all authorized resources
  • Scalability: Handles from 10 to millions of objects
  • Delegation: Grant specific admin rights without full Domain Admin access
  • Auditing: Track who accessed what and when

1.3 AD DS vs Workgroup

FeatureWorkgroupActive Directory Domain
User accountsLocal to each computerCentralized on Domain Controllers
AuthenticationPer-machineDomain-wide via Kerberos
Policy managementLocal Group Policy onlyDomain Group Policy (GPO)
ScaleUp to ~20 computersUnlimited
AdministrationPer computerCentralized
SecurityInconsistentConsistent, auditable
Domain Controller (DC) is the heart of AD. It runs AD DS, authenticates users, stores the AD database (NTDS.DIT), and applies Group Policy. Always have at least two DCs for redundancy — if your only DC goes down, nobody can log in. Ever.

2.2 Distinguished Names (DN)

Every object in AD has a unique Distinguished Name that describes its exact location in the directory.

! Format: CN=CommonName, OU=OrganizationalUnit, DC=DomainComponent

! Example — User John Smith in the Faculty OU:
CN=John Smith,OU=Faculty,OU=Staff,DC=tstc,DC=edu

! Example — Computer LABPC01 in the Computers OU:
CN=LABPC01,OU=Computers,OU=Labs,DC=tstc,DC=edu

! Example — Group "IT Admins":
CN=IT Admins,OU=Groups,DC=tstc,DC=edu

! Components:
! CN  = Common Name (the object's name)
! OU  = Organizational Unit (container)
! DC  = Domain Component (tstc.edu = DC=tstc,DC=edu)

3. AD Physical Structure

3.1 Domain Controllers

  • Servers running AD DS role — store and replicate the AD database
  • NTDS.DIT — the actual AD database file (located in C:\Windows\NTDS\)
  • SYSVOL — shared folder replicated to all DCs — contains GPO templates and logon scripts (C:\Windows\SYSVOL\)
  • All DCs are peers — multi-master replication (any DC can accept changes)
  • Read-Only Domain Controllers (RODC) — used in branch offices — receive but don't originate changes

3.2 AD Sites

  • A site represents a physical location with fast, reliable network connectivity
  • Defined by one or more IP subnets
  • AD uses site information to optimize authentication (clients authenticate to nearest DC) and replication (control when and how much replication traffic crosses slow WAN links)
  • Site Link: Defines connection between sites — set cost and replication interval
  • Site Link Bridge: Connects site links — usually all site links are bridged by default
  • Default replication interval within a site: 15 seconds
  • Default replication interval between sites: 180 minutes (configurable)

4. Installing AD DS Lab Heavy

4.1 Prerequisites

  • Windows Server 2016/2019/2022 (Standard or Datacenter)
  • Static IP address configured on the server
  • DNS server configured — ideally point to itself after AD install
  • Computer name set before promotion (can't easily change after)
  • Strong password for DSRM (Directory Services Restore Mode)

4.2 Installing AD DS via PowerShell

# Step 1: Install the AD DS role
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools

# Step 2a: Promote to NEW forest (first DC)
Install-ADDSForest `
    -DomainName "tstc.edu" `
    -DomainNetbiosName "TSTC" `
    -DomainMode "WinThreshold" `       # Windows Server 2016 functional level
    -ForestMode "WinThreshold" `
    -InstallDns:$true `                # Install DNS with AD
    -SafeModeAdministratorPassword (ConvertTo-SecureString "P@ssw0rd123!" -AsPlainText -Force) `
    -Force:$true

# Step 2b: Promote to ADDITIONAL DC in existing domain
Install-ADDSDomainController `
    -DomainName "tstc.edu" `
    -InstallDns:$true `
    -Credential (Get-Credential) `
    -SafeModeAdministratorPassword (ConvertTo-SecureString "P@ssw0rd123!" -AsPlainText -Force) `
    -Force:$true

# Step 2c: Add a CHILD domain
Install-ADDSDomain `
    -NewDomainName "west" `
    -ParentDomainName "tstc.edu" `     # Creates west.tstc.edu
    -DomainMode "WinThreshold" `
    -InstallDns:$true `
    -Credential (Get-Credential) `
    -SafeModeAdministratorPassword (ConvertTo-SecureString "P@ssw0rd123!" -AsPlainText -Force) `
    -Force:$true

4.3 Post-Installation Verification

# Verify AD is running
Get-Service adws, kdc, netlogon, dns

# Check DC info

# Check domain info
Get-ADDomain

# Check forest info

DSRM password — don't forget it. Directory Services Restore Mode is the recovery mode for AD. You need this password to restore AD from backup or repair a corrupted database. It's separate from the normal admin password. Write it down and store it securely — if your AD breaks and you don't have this, you're in serious trouble.

7. Organizational Units (OUs) Lab Heavy

7.1 OU Design Principles

  • OUs are containers for organizing AD objects — users, computers, groups, printers
  • GPOs are linked to OUs — objects in an OU inherit its GPOs
  • Delegation of control is applied at the OU level
  • Design OUs based on GPO application needs and delegation needs — not just org chart
  • Keep OU structure as flat as possible — deep nesting = complex GPO troubleshooting

7.2 Common OU Structure

tstc.edu
├── OU=Staff
│   ├── OU=Faculty
│   │   ├── CN=John Smith (user)
│   │   └── CN=Adrian Medrano (user)
│   └── OU=Administrative
├── OU=Students
│   ├── OU=CNS
│   └── OU=IT
├── OU=Computers
│   ├── OU=Labs
│   │   ├── OU=CNS-Lab
│   │   └── OU=IT-Lab
│   └── OU=Faculty-Computers
├── OU=Groups
│   ├── OU=Security-Groups
│   └── OU=Distribution-Groups
└── OU=Service-Accounts

7.3 OU Management — PowerShell

# ===== CREATE OUs =====
New-ADOrganizationalUnit -Name "Faculty" -Path "OU=Staff,DC=tstc,DC=edu" -ProtectedFromAccidentalDeletion $true

# ===== PROTECT FROM ACCIDENTAL DELETION =====
Set-ADOrganizationalUnit -Identity "OU=Faculty,OU=Staff,DC=tstc,DC=edu" -ProtectedFromAccidentalDeletion $true

# ===== REMOVE PROTECTION (required before deleting) =====
Set-ADOrganizationalUnit -Identity "OU=Faculty,OU=Staff,DC=tstc,DC=edu" -ProtectedFromAccidentalDeletion $false

# ===== DELETE OU =====
Remove-ADOrganizationalUnit -Identity "OU=Faculty,OU=Staff,DC=tstc,DC=edu" -Recursive -Confirm:$false

# ===== DELEGATION OF CONTROL =====
# Grant HelpDesk group ability to reset passwords in Students OU
# This is done in GUI: ADUC → Right-click OU → Delegate Control
# PowerShell version:
$ou = "OU=Students,DC=tstc,DC=edu"
$group = Get-ADGroup "HelpDesk"
$acl = Get-Acl "AD:$ou"
# Full delegation scripting requires System.DirectoryServices — use GUI for simple cases
Always enable "Protect from accidental deletion" on every OU you create. Without it, someone with the right permissions can delete an OU and everything inside it with one click — users, computers, groups, all gone. The protection adds a deny ACE that prevents deletion without first removing the protection.

8. Group Policy (GPO) Lab Heavy

8.1 GPO Basics

  • Group Policy Objects (GPOs) define settings applied to users and computers
  • GPOs are linked to: Sites, Domains, or OUs
  • Settings are divided: Computer Configuration (applied at startup) and User Configuration (applied at logon)
  • Stored in SYSVOL and AD — replicated to all DCs
  • Default GPOs: Default Domain Policy (password policy, account lockout) and Default Domain Controllers Policy (DC security settings)

8.2 GPO Processing Order — LSDOU

  1. Local — local Group Policy on the machine itself (lowest priority)
  2. Site — GPOs linked to the AD site
  3. Domain — GPOs linked to the domain
  4. OU — GPOs linked to OUs, parent to child order (highest priority — wins conflicts)

🧠 Remember: Last applied wins. OU GPOs override Domain GPOs which override Site GPOs which override Local. The deeper the OU, the higher the priority.

8.3 GPO Inheritance & Enforcement

OptionWhere SetEffect
Block InheritanceOn OUPrevents parent GPOs from flowing down to this OU
Enforced (No Override)On GPO linkGPO settings cannot be blocked — always wins regardless of Block Inheritance
Link Enabled/DisabledOn GPO linkTemporarily disable a GPO link without deleting
GPO Enabled/DisabledOn GPODisable entire GPO or just Computer/User portion
Security FilteringOn GPOApply GPO only to specific users/groups — default is Authenticated Users

8.4 Common GPO Settings

! ===== PASSWORD POLICY (Domain level — Default Domain Policy) =====
Computer Config → Policies → Windows Settings → Security Settings → Account Policies → Password Policy:
  - Minimum password length: 12
  - Maximum password age: 90 days
  - Minimum password age: 1 day
  - Password history: 24 passwords remembered
  - Complexity requirements: Enabled
  - Reversible encryption: Disabled

! ===== ACCOUNT LOCKOUT POLICY =====
Computer Config → Account Policies → Account Lockout Policy:
  - Account lockout threshold: 5 attempts
  - Account lockout duration: 30 minutes
  - Reset lockout counter after: 30 minutes

! ===== COMMON COMPUTER SETTINGS =====
Computer Config → Policies → Windows Settings → Security Settings:
  - Rename administrator account
  - Disable guest account
  - Restrict access to Control Panel
  - Configure Windows Firewall
  - Deploy software (MSI packages)
  - Configure startup/shutdown scripts

! ===== COMMON USER SETTINGS =====
User Config → Policies → Administrative Templates:
  - Remove Run from Start menu
  - Prevent access to registry editing tools
  - Disable command prompt
  - Map network drives (User Config → Windows Settings → Drive Maps via Preferences)
  - Configure Internet Explorer/Edge settings
  - Folder Redirection (My Documents → network share)

9. DNS Integration with Active Directory

9.1 Why AD Needs DNS

  • AD is completely dependent on DNS — everything uses DNS to find DCs and services
  • Clients use DNS to locate Domain Controllers via SRV records
  • AD-integrated DNS stores zone data in AD itself — replicated automatically to all DCs
  • Without proper DNS, domain joins fail, authentication fails, GPO fails

10. DHCP with Active Directory

10.1 DHCP Server Authorization

  • In an AD domain, DHCP servers must be authorized in AD before they can serve addresses
  • Prevents rogue DHCP servers from handing out bad addresses
  • Only domain admins (or delegated users) can authorize DHCP servers
  • Unauthorized DHCP server detects authorized server and shuts down automatically

11. AD Replication & Sites

11.1 Replication Concepts

  • AD uses multi-master replication — changes can be made on any DC
  • Changes replicate to all other DCs — eventually consistent
  • USN (Update Sequence Number): Tracks changes per DC — monotonically increasing
  • Originating write: The first DC to receive a change
  • Replication latency: Time for change to propagate to all DCs
  • Replication conflicts: Same attribute changed on two DCs — last writer wins (based on timestamp)

11.2 Replication Topology

  • KCC (Knowledge Consistency Checker): Automatic process that builds the replication topology
  • Creates a ring topology within a site — max 3 hops between any two DCs
  • Between sites — uses site links you define manually
  • Connection objects: Define replication partnerships between DCs

11.3 Replication Management

# ===== CHECK REPLICATION STATUS =====
repadmin /showrepl                         # Replication status for all partners
repadmin /replsummary                      # Summary — quick health check
repadmin /showrepl dc1.tstc.edu            # Specific DC replication status

# ===== FORCE IMMEDIATE REPLICATION =====
repadmin /syncall                          # Sync all DCs
repadmin /syncall dc1.tstc.edu /AdeP       # Sync specific DC — all partitions

# ===== CHECK FOR REPLICATION ERRORS =====
repadmin /showrepl * /errorsonly           # Only show errors
dcdiag /test:replications                 # Replication diagnostics

# ===== SITE AND SITE LINK MANAGEMENT =====

12. Authentication — Kerberos & NTLM

12.1 Kerberos Authentication

Kerberos is the default authentication protocol in Active Directory. It uses tickets issued by the KDC (Key Distribution Center — part of every DC) to grant access to resources without sending passwords over the network.

  1. AS-REQ: Client sends encrypted timestamp to KDC (Authentication Service)
  2. AS-REP: KDC returns TGT (Ticket Granting Ticket) encrypted with user's password hash
  3. TGS-REQ: Client presents TGT to KDC's Ticket Granting Service, requests service ticket
  4. TGS-REP: KDC returns service ticket (encrypted with server's key)
  5. AP-REQ: Client presents service ticket directly to target server
  6. AP-REP: Server validates ticket, grants access — no password ever sent on network

12.2 Kerberos Requirements

  • Time synchronization: All machines within 5 minutes of DC — Kerberos rejects stale tickets
  • DNS: Forward and reverse DNS must work properly
  • SPNs (Service Principal Names): Register services so Kerberos can find the right server key
  • Kerberos uses UDP/TCP port 88

12.3 NTLM — Fallback Authentication

  • Used when Kerberos fails — older servers, IP address connections, non-domain systems
  • Challenge-response protocol — less secure than Kerberos
  • NTLMv2 is acceptable; NTLMv1 is broken — disable it via GPO
  • NTLM doesn't support mutual authentication — server can't prove its identity to client

13. FSMO Roles

13.1 The Five FSMO Roles

Flexible Single Master Operation roles handle tasks that can only be performed by one DC at a time (to avoid conflicts). There are 5 FSMO roles — 2 forest-wide, 3 domain-wide.

RoleScopeResponsible For
Schema MasterForest-wide (1 per forest)All changes to the AD schema (object types and attributes)
Domain Naming MasterForest-wide (1 per forest)Adding and removing domains from the forest
RID MasterDomain-wide (1 per domain)Allocates pools of RIDs (Relative IDs) to DCs — RIDs are part of SIDs
PDC EmulatorDomain-wide (1 per domain)Password changes, account lockouts, time sync source, legacy NT compatibility
Infrastructure MasterDomain-wide (1 per domain)Updates cross-domain group-to-user references
PDC Emulator is the most critical FSMO role. It handles password changes and account lockouts — if it goes down, users can't change passwords and lockout policies may not work correctly. It's also the time source for all other DCs in the domain. Make sure it's on a reliable, well-connected DC.

13.2 FSMO Role Management

# ===== VIEW CURRENT FSMO ROLE HOLDERS =====
netdom query fsmo                          # Quick view of all 5 roles
Get-ADForest | Select-Object SchemaMaster, DomainNamingMaster
Get-ADDomain | Select-Object RIDMaster, PDCEmulator, InfrastructureMaster

# ===== TRANSFER FSMO ROLES (graceful — old DC must be online) =====
Move-ADDirectoryServerOperationMasterRole `
    -Identity "DC2" `
    -OperationMasterRole PDCEmulator, RIDMaster, InfrastructureMaster

# ===== SEIZE FSMO ROLES (old DC is dead — use with caution) =====
# Never bring the old DC back online after seizing!
Move-ADDirectoryServerOperationMasterRole `
    -Identity "DC2" `
    -OperationMasterRole PDCEmulator `
    -Force

14. AD Backup & Recovery Lab Heavy

14.1 AD Backup Strategy

  • Back up System State — includes AD database (NTDS.DIT), SYSVOL, registry, boot files
  • Back up at least one DC per domain — ideally all DCs
  • Test restores regularly — a backup you've never tested is not a backup
  • AD Recycle Bin (enabled feature) — recover accidentally deleted objects without restore
  • Backup should be more recent than the tombstone lifetime (default 180 days)

14.2 Backup & Restore Commands

# ===== INSTALL WINDOWS SERVER BACKUP =====
Install-WindowsFeature Windows-Server-Backup

# ===== BACKUP SYSTEM STATE (includes AD) =====
wbadmin start systemstatebackup -backuptarget:E: -quiet

# ===== BACKUP ENTIRE SERVER =====
wbadmin start backup -backuptarget:\\server\share -include:C: -allCritical -quiet

# ===== ENABLE AD RECYCLE BIN (do this early!) =====
Enable-ADOptionalFeature `
    -Identity "Recycle Bin Feature" `
    -Scope ForestOrConfigurationSet `
    -Target "tstc.edu" `
    -Confirm:$false

# ===== RESTORE DELETED OBJECT FROM RECYCLE BIN =====
Get-ADObject -Filter {DisplayName -eq "John Smith"} -IncludeDeletedObjects
Restore-ADObject -Identity 

# ===== AUTHORITATIVE RESTORE (boot into DSRM) =====
# Used when AD data was accidentally deleted and Recycle Bin not enabled
# 1. Reboot DC, press F8, select "Directory Services Restore Mode"
# 2. Log in with DSRM password
# 3. Restore system state backup:
#    wbadmin start systemstaterecovery -version:
# 4. Mark objects as authoritative so they replicate outward:
#    ntdsutil → authoritative restore → restore subtree "OU=Faculty,DC=tstc,DC=edu"
# 5. Restart normally

# 53   — DNS (TCP/UDP)

# 135  — RPC Endpoint Mapper
# 139  — NetBIOS Session Service
# 389  — LDAP (TCP/UDP)

# 464  — Kerberos password change
# 636  — LDAPS (encrypted LDAP)
# 3268 — Global Catalog LDAP
# 3269 — Global Catalog LDAPS
# 49152-65535 — Dynamic RPC ports (replication)
Always change passwords on the PDC Emulator first. When you reset a password in AD, it replicates to all DCs — but replication takes time. If a user gets locked out and you reset their password on DC2, but they try to log in through DC1 which hasn't replicated yet, it may still reject them. Reset on the PDC Emulator, which replicates the change out immediately to all other DCs.
