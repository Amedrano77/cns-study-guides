1. Cloud Concepts & Models Domain 1

1.1 What is Cloud Computing?

The NIST definition: Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (networks, servers, storage, applications, services) that can be rapidly provisioned and released with minimal management effort or service provider interaction.

1.2 Five Essential Characteristics (NIST)

CharacteristicDescription
On-Demand Self-ServiceProvision resources automatically without human interaction from provider — spin up a VM in minutes
Broad Network AccessCapabilities available over the network via standard mechanisms — accessible from any device, anywhere
Resource PoolingProvider's resources pooled to serve multiple consumers — multi-tenant model with dynamic assignment
Rapid ElasticityResources can be rapidly and elastically provisioned — scale up or down automatically based on demand
Measured ServiceResource usage automatically monitored and reported — pay only for what you use (metered billing)

1.3 Cloud Deployment Models

ModelDescriptionWho ManagesUse Case
Public CloudInfrastructure owned and operated by third-party provider — shared with other customersProviderWeb apps, startups, variable workloads
Private CloudCloud infrastructure used exclusively by one organization — on-premises or hostedOrganization or managed providerRegulated industries, sensitive data, consistent workloads
Hybrid CloudCombines public and private — data and apps shared between themBothSensitive data stays private, burst to public for peak demand
Community CloudShared by several organizations with common interestsOne or more orgs or providerGovernment agencies, healthcare groups, research
Multi-CloudUsing two or more public cloud providers simultaneouslyOrganizationAvoid vendor lock-in, best-of-breed services

1.4 Cloud Business Drivers

  • CapEx → OpEx: Convert capital expenditure (buy servers) to operational expenditure (monthly bill)
  • Economies of scale: Provider buys hardware in massive volume — passes savings to customers
  • Speed to market: Launch new services in hours vs. months for physical infrastructure
  • Global reach: Deploy to any region in the world instantly
  • Focus on core business: Stop managing datacenters — focus on your product
  • Disaster recovery: Built-in redundancy and geo-replication at low cost
Cloud+ is vendor-neutral but the exam is AWS-heavy in examples. Know all concepts generically first, then map them to AWS, Azure, and GCP equivalents. When the exam says "object storage" think S3. When it says "virtual machine service" think EC2. The concepts are the same — just different brand names.

3.2 Resource Tagging & Organization

  • Tags: Key-value metadata labels applied to cloud resources — used for billing, organization, automation, access control
  • Resource Groups: Logical containers grouping related resources (Azure) or similar concept via tagging (AWS)
  • Accounts/Projects: Top-level isolation boundary — separate accounts per environment (dev/staging/prod) is best practice
  • Naming conventions: Consistent names across all resources — environment, region, resource type: prod-us-east-web-01

4.2 Object Storage Deep Dive

  • Bucket: Top-level container for objects (like a folder at the root)
  • Object: The actual file + metadata + unique key
  • Key: Unique identifier for an object within a bucket — looks like a path but isn't really
  • Versioning: Keep multiple versions of same object — protects against accidental deletion
  • Lifecycle policies: Automatically move objects to cheaper storage tiers or delete after set time
  • Storage classes: Standard (frequent access), Infrequent Access, Glacier (archive) — balance cost vs. retrieval speed

4.3 Storage Performance Concepts

TermDefinition
IOPSInput/Output Operations Per Second — measures storage performance for small random reads/writes
ThroughputMB/s transferred — measures sequential read/write performance (large files, streaming)
LatencyTime to complete one I/O operation — block storage has ms latency, archive has minutes
DurabilityProbability data survives — AWS S3 = 99.999999999% (11 nines) durability
AvailabilityPercentage of time storage is accessible — S3 Standard = 99.99% availability
Thin ProvisioningAllocate more storage than physically exists — relies on not all being used simultaneously

5. Cloud Networking Domain 2

5.1 Virtual Private Cloud (VPC)

  • A VPC is a logically isolated section of the cloud provider's network — your private network in the cloud
  • You define the IP address range (CIDR block), subnets, route tables, and gateways
  • Subnets: Subdivide the VPC — public subnets (internet accessible), private subnets (internal only)
  • Public subnet: Has a route to the Internet Gateway — instances can be reached from internet
  • Private subnet: No direct internet route — must use NAT Gateway to initiate outbound connections

5.4 Content Delivery Network (CDN)

  • CDN caches content at edge locations globally — reduces latency for end users by serving from nearest location
  • Reduces load on origin servers — edge serves cached responses
  • AWS CloudFront, Azure CDN, Cloudflare are common CDNs
  • Best for: static assets (images, CSS, JS), video streaming, large file downloads, DDoS mitigation
Security Groups vs NACLs: Security Groups are stateful — if you allow inbound traffic, the response is automatically allowed outbound. NACLs are stateless — you must explicitly allow both inbound AND outbound. Security Groups operate at the instance level; NACLs at the subnet level. Use both for defense in depth.

6.4 Serverless Computing

  • No server management — provider handles all infrastructure
  • Code runs in stateless functions triggered by events
  • Pay per execution — billed in milliseconds, not per hour
  • Auto-scales automatically — from zero to thousands of executions instantly
  • Cold start: First invocation after idle period has higher latency — container must initialize
  • AWS Lambda: max 15 minute execution, 10GB RAM, 512MB–10GB temp storage

7. Cloud Security Domain 3

7.1 Cloud Security Principles

  • Defense in Depth: Multiple layers of security controls — never rely on one control
  • Least Privilege: Grant minimum permissions needed — nothing more
  • Zero Trust: Never trust, always verify — authenticate and authorize every request regardless of location
  • Encryption Everywhere: Data encrypted at rest AND in transit — no exceptions
  • Immutable Infrastructure: Don't patch running systems — replace them with new images
  • Shift Left Security: Integrate security into development pipeline — not bolted on at the end

8. Identity & Access Management (IAM) Domain 3

8.1 IAM Core Concepts

TermDefinition
UserAn identity representing a person or application — has credentials (username/password, access keys)
GroupCollection of users — attach policies to group, members inherit permissions
RoleIdentity with permissions that can be assumed temporarily — used by services, apps, cross-account access
PolicyJSON document defining what actions are allowed/denied on which resources
PermissionThe actual allow/deny for a specific action on a specific resource
Principle of Least PrivilegeGrant only the minimum permissions needed — nothing more

8.2 IAM Best Practices

  • Never use root account for daily operations — create individual IAM users
  • Enable MFA on root and all privileged accounts
  • Use roles instead of access keys for applications running on AWS services
  • Rotate credentials regularly — access keys, passwords
  • Use groups to assign permissions — not directly to users
  • Enable IAM Access Analyzer — identifies overly permissive policies
  • Enforce strong password policy — minimum length, complexity, rotation

12.2 Cloud Cost Optimization

  • Right-sizing: Match instance size to actual workload — most instances are over-provisioned
  • Reserved/Savings Plans: Commit to 1–3 year usage for up to 72% discount
  • Spot instances: Use interruptible spot for fault-tolerant workloads — up to 90% cheaper
  • Auto Scaling: Scale down during low-demand periods — don't pay for idle capacity
  • Storage tiering: Move infrequently accessed data to cheaper storage classes automatically
  • Delete idle resources: Unused EIPs, unattached volumes, old snapshots — all cost money
  • Use managed services: Often cheaper than running equivalent on EC2 when you factor in admin time

13.2 Cloud Troubleshooting Tools

# ===== AWS CLI — essential troubleshooting commands =====

# Check EC2 instance status
aws ec2 describe-instances --instance-ids i-1234567890abcdef0
aws ec2 describe-instance-status --instance-ids i-1234567890abcdef0

# Check security groups
aws ec2 describe-security-groups --group-ids sg-12345678

# View VPC flow logs (network traffic analysis)
aws logs filter-log-events --log-group-name VPCFlowLogs --filter-pattern "REJECT"

# Check IAM permissions
aws iam simulate-principal-policy \
    --policy-source-arn arn:aws:iam::123456789012:user/test-user \
    --action-names s3:GetObject \
    --resource-arns arn:aws:s3:::my-bucket/*

# View CloudTrail events (who did what)
aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=StopInstances

# Check CloudWatch metrics
aws cloudwatch get-metric-statistics \
    --namespace AWS/EC2 \
    --metric-name CPUUtilization \
    --dimensions Name=InstanceId,Value=i-1234567890abcdef0 \
    --start-time 2024-01-15T00:00:00Z \
    --end-time 2024-01-15T23:59:59Z \
    --period 3600 --statistics Average

The AWS Well-Architected Framework has 6 pillars — know them cold for Cloud+: Operational Excellence (run and monitor systems), Security (protect data and systems), Reliability (recover from failures), Performance Efficiency (use resources efficiently), Cost Optimization (avoid unnecessary costs), and Sustainability (minimize environmental impact). Every architecture decision maps to one or more of these pillars.
